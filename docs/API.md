# Court interfaces

The CLI, REST API, and official MCP SDK server share the same validated service operations. A registered adapter is metadata, not a claim that a portal has been tested live. `get_source_capabilities` reports `fixture`, `documented`, or `live` evidence, source result caps, unsupported searches, and limitations. The independent fixture is not a second live state portal. Live Minnesota access requires explicit source opt-in; challenges stop acquisition rather than trigger identity or proxy changes.

## Configuration and authorization

Run migrations before starting a service:

```sh
node dist/src/platform/courtctl.js db migrate
node dist/src/platform/api.js
```

`COURT_DATABASE_URL` is required. Configure storage using `COURT_STORAGE_DIR` or the deployment's GCS settings. REST requires all three distinct, nonempty secrets: `API_TOKEN_READ`, `API_TOKEN_WRITE`, and `API_TOKEN_ADMIN`. Use high-entropy secrets from a secret manager. Authenticate with `Authorization: Bearer <token>`; never put tokens in query strings. The role hierarchy is read < acquire < admin. The server defaults to `HOST=0.0.0.0`, `PORT=3000`. Serve behind TLS. The primary 120 requests/minute limit is backed by PostgreSQL and shared across API replicas; the persisted principal is a SHA-256 token digest, never the bearer credential. A denied admission returns 429 and `Retry-After: 60`. Admission failures fail closed. Source acquisition budgets are enforced separately through durable jobs.

All routes, including health, metrics and OpenAPI, require authentication. Read permits local searches and evidence retrieval; acquire also permits acquisition, bulk and refresh requests. Administrative retries, cancellation, restriction, discovery scheduling, legacy import, storage verification and metrics require admin. The CLI is explicitly trusted local administration, without API tokens; limit filesystem and shell access accordingly.

Successful mutating operations write audit events with the interface actor, operation, resource identifier where available, and role. API actors use the same token digest; CLI uses `local:cli` and MCP uses `mcp:<role>`. Tokens and full request payloads are not included in these audit events.

## REST

Prefix: `/api/v1`. Runtime OpenAPI: `GET /api/v1/openapi.json` with a read token. Schemas are generated by Fastify Swagger from the same Zod operation schemas used for validation. Unknown keys are rejected, not discarded; bulk query items are validated individually by the service so an invalid item does not discard valid neighbors. JSON request bodies are limited to 2 MiB. Internal database, filesystem and credential details are not returned in error bodies.

| Method | Path | Role | Input / purpose |
| --- | --- | --- | --- |
| GET | `/sources` | read | Registered metadata |
| GET | `/sources/:sourceId/capabilities` | read | Source search requirements and caps |
| GET | `/cases` | read | Database search filters |
| GET | `/docket-entries` | read | Database docket search filters |
| GET | `/filing-text` | read | Database extracted-text search filters |
| GET | `/cases/:id` | read | Internal case UUID |
| GET | `/cases/:id/docket` | read | `limit`, `offset` |
| GET | `/filings/:id` | read | Internal filing/document UUID |
| GET | `/documents/:id/text` | read | `limit`, `offset` |
| GET | `/documents/:id/content` | read | Original artifact bytes with sanitized attachment filename; no storage paths |
| GET | `/jobs/:id` | read | Durable status, partial/failure evidence |
| GET | `/coverage` | read | `sourceId`, `state`, `court`, `county`, `category`, `filedFrom`, `filedTo`, `limit`, `offset` |

| POST | `/acquisitions` | acquire | `{ "query": <source query> }` |

| POST | `/storage/verify` | admin | Verify persisted artifacts |

The three acquisition/bulk/refresh endpoints require `Idempotency-Key`. Keys are 1–200 ASCII letters, digits, `.`, `_`, `:`, or `-`. Preserve the same key when retrying the same request; use a different key for different work. They return HTTP 202 with the service's durable job result, not a completed acquisition. Administrative job retry means retrying an existing job, not resubmitting a new acquisition.

Job responses distinguish aggregate workflow `status` (also explicit as `workflowStatus`) from the root job's `stageStatus`. A completed root stage is not reported as a completed workflow while dependent work remains pending.

Database filters are `sourceId`, `state`, `caseId`, `caseNumber`, `q`, `status`, `court`, `county`, `party`, `attorney`, `judge`, `category`, `filedFrom`, `filedTo`, `documentType`, `citation`, and `organization`. Filters unsupported by a particular search are rejected by the service. Dates use `YYYY-MM-DD`; IDs for stored resources are UUIDs, not source case numbers. Pagination defaults to `limit=50&offset=0`; maximum limit 100 and offset 100000. Collection responses preserve the service's `{data, meta:{limit,offset,hasMore}, coverageNote}` envelope. Follow `hasMore` with the next offset; a local result set is not proof of complete court coverage.

Database ordering accepts `sortBy=observedAt|caseNumber|court|status|filedDate` and `sortOrder=asc|desc` (CLI: `--sort-by`, `--sort-order`). Unsupported sort values are rejected. Coverage filters are specifically `sourceId`, `state`, `court`, `county`, `category`, `filedFrom`, `filedTo`, `limit`, and `offset`; unrelated database filters are rejected. Coverage `state` is a stored-data filter and does not imply a live source registration.

Source queries require `searchType` (`case`, `party`, `business`, `attorney`, `hearing`, `judgment`, or `document`) and default `sourceId` to `mn-mcro`. Allowed search fields are `caseNumber`, `citationNumber`, `lastName`, `firstName`, `middleName`, `businessName`, `attorneyLastName`, `attorneyFirstName`, `attorneyMiddleName`, `barNumber`, `judgeName`, `soundex`, `county`, `counties`, `categories`, `status`, `filedFrom`, `filedTo`, `hearingFrom`, `hearingTo`, `dobFrom`, `dobTo`, `docketedFrom`, `docketedTo`, `judgmentStatus`, and `acquireResults`. Source capabilities determine which combinations are supported; interfaces do not claim all modes work on every source. No URL field or arbitrary browser-navigation tool exists. `acquireResults=false` requests source search observation without acquiring every result. A batch supports at most 1000 heterogeneous queries; per-query `acquireResults` overrides the optional batch value.

```sh
curl -H "Authorization: Bearer $API_TOKEN_READ" \
  'http://localhost:3000/api/v1/cases?q=housing&limit=20&offset=0'

curl -X POST -H "Authorization: Bearer $API_TOKEN_WRITE" \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: example-request-1' \
  -d '{"query":{"sourceId":"mn-mcro","searchType":"case","caseNumber":"27-CV-24-1"}}' \
  'http://localhost:3000/api/v1/acquisitions'
```

Examples illustrate request structure, not an observed case or live acquisition. Errors use `{ "error": { "code": "...", "message": "..." } }`: 400 invalid input, 401 missing/invalid credential, 403 role/restriction denial, 404 missing resource, 409 conflict, 413 oversized input, 422 unsupported/invalid source operation, 429 throttling, 502 source parse failure, 503 blocked/retryable source, or 500 unexpected failure.

## CLI

Use `node dist/src/platform/courtctl.js --help` for the full command tree. Commands return JSON, with diagnostics to stderr and nonzero exit on error. `--source` selects a registered source ID; `--state MN` maps to `mn-mcro` for source operations. Other states are not silently mapped. Source selection is separate from the database `--state` filter.

```sh
courtctl sources list
courtctl source caps --state MN
courtctl source search --state MN --query '{"searchType":"party","lastName":"Smith","firstName":"Alex"}' --idempotency-key search-smith-1
courtctl acquire --source mn-mcro --query '{"searchType":"case","caseNumber":"27-CV-24-1"}' --idempotency-key case-1
courtctl db search --q housing --limit 20 --offset 0
courtctl db docket-search --party Smith
courtctl db filing-search --q contract
courtctl case get UUID
courtctl case docket UUID --limit 20
courtctl case refresh UUID --idempotency-key refresh-1
courtctl case watch UUID --enabled true
courtctl case watch UUID --enabled false
courtctl refresh-policy get
courtctl refresh-policy set --policy '{"watchedMinutes":30,"newMinutes":180}'
courtctl case restrict UUID --reason 'Court restriction verified'
courtctl filing get UUID
courtctl document text UUID --limit 20
courtctl jobs status UUID
courtctl jobs retry UUID
courtctl jobs cancel UUID
courtctl coverage --source mn-mcro --state MN --county Hennepin --category Civil --filed-from 2024-01-01 --filed-to 2024-12-31
courtctl discovery plan --query '{"sourceId":"mn-mcro","searchType":"party","lastName":"Smith"}'
courtctl schedule due
courtctl doctor
courtctl storage verify
courtctl metrics
courtctl import-legacy --directory /path/to/legacy
courtctl db migrate
```

`courtctl` denotes the installed command; invoke the built JavaScript directly if not installed. `UUID` is a placeholder for an actual internal identifier. The worker is a separate process; CLI commands do not bypass its source budgets or synchronously drive a portal.

### Adaptive refresh and acquisition consent

Metadata-only source search (`acquireResults=false`) and metadata-only imports do not enroll new cases in acquisition. Migration 0009 removes the old implicit `next_refresh_at=now()` default, clears unintentional schedules with no docket/explicit refresh intent, and cancels their implicit queued refreshes. Existing explicitly tracked cases remain tracked when rediscovered by a metadata-only search.

`case watch UUID --enabled true` explicitly opts that known identifier into recurring acquisition and gives its refresh jobs priority 100 (ordinary refresh: 0). Disabling watch removes priority and returns an already tracked case to normal scheduling; it does **not** erase evidence or cancel normal tracking. Watch changes require acquire permission and policy changes require admin; both are audited. The MCP equivalents are `set_case_watch({id,enabled})`, `get_refresh_policy({})`, and `set_refresh_policy({policy:{...}})`.

The singleton PostgreSQL policy survives process restarts. Integer intervals are in minutes; observation windows are in days. Partial updates reject unknown fields. Current defaults:

| Class / policy field | Default |
| --- | --- |
| Watched / `watchedMinutes` | 60 minutes |
| Newly discovered tracked / `newMinutes` | 360 minutes |
| Recently changed / `recentMinutes` | 720 minutes |
| Older active or unknown status / `activeMinutes` | 1440 minutes |
| Inactive / `inactiveMinutes` | 10080 minutes (7 days) |
| Closed or disposed / `closedMinutes` | 43200 minutes (30 days) |
| Incomplete docket / `partialMinutes` | 120 minutes |
| Exhausted refresh failure / `failedMinutes` | 360 minutes |
| New discovery window / `newWindowDays` | 7 days |
| Recent observed activity window / `recentWindowDays` | 30 days |

Classification precedence is watched, failed, partial, closed/inactive, new, recently changed, older active. New/recent boundaries are exclusive: at exactly the configured age the next applicable class wins. All non-dormant intervals are constrained to 1–1440 minutes; inactive/closed intervals to 1–525600 minutes; windows to 1–365 days. Unknown source-specific status labels stay active; these labels are not a cross-jurisdiction taxonomy.

`case_refresh_evidence` derives first/latest observation, snapshot count, meaningful changed-observation count, last meaningful observed activity and change frequency from immutable snapshots, semantic entry changes and observed status history. Frequency is changed observations divided by post-baseline observations; initial inventory, replay, DOM reordering and local identity migration are not court activity. No filing/event timestamp is treated as a newly observed change. The live projection includes pre-migration evidence without a separate import. `cases.refresh_class` and `refresh_interval_minutes` record the latest scheduling decision.

Policy shortening caps existing tracked deadlines; increases take effect on the next scheduling decision without postponing already promised work. Enqueuing and next-deadline persistence are atomic. Manual refreshes have a durable request job whose child shares an already active refresh, preserving caller idempotency and workflow status. Source-search root completion means search observation only, not successful downstream acquisition.

Run `schedule due` regularly (the worker does so automatically). Discovery keeps its own persisted deadlines independently of case refresh. Concurrent schedulers skip locked rows and reuse due keys; work survives restarts. Permanent refresh failures stop automatic scheduling and require explicit retry. Exhausted transient discovery failures get at most two recovery generations, with six-/twelve-hour backoff; permanent or exhausted partitions stop with an explicit gap until `discovery plan` intentionally replans. Closed cases periodically recheck. The ≤24-hour active refresh interval is a scheduling target, not a source availability/completeness promise; policy, pauses and backlog can delay observation.


### Structured batches

```sh
courtctl bulk --file requests.json --idempotency-key batch-1
courtctl bulk --file requests.jsonl --idempotency-key batch-2
courtctl bulk --file requests.csv --format csv --idempotency-key batch-3
```

JSON accepts an array of source queries or `{ "queries": [...], "acquireResults": false }`. JSONL contains one query object per nonempty line. CSV uses exact camelCase query field names as headers, not CLI flag names; blank cells are omitted. Boolean fields must be `true` or `false`; `counties` and `categories` cells contain quoted JSON arrays. Formats are inferred from the filename or selected explicitly. Parsing preserves heterogeneous search modes and invalid query items for individual service validation: an unknown/unsafe field, invalid boolean, or malformed array cell produces that item's validation result without losing valid neighbors. Invalid JSON/CSV file syntax or an invalid batch envelope is rejected as a whole. Files are streamed with a 2 MiB cap; batch query count is capped at 1000.

## MCP stdio

Launch `node dist/src/platform/mcp.js`. This uses `McpServer`, `registerTool`, and `StdioServerTransport` from the installed official SDK; stdout is reserved for protocol messages. Default `MCP_ROLE=read` exposes only read tools. For acquisition set `MCP_ROLE=acquire` and `MCP_TOKEN` equal to `API_TOKEN_WRITE`. For administration set `MCP_ROLE=admin` and `MCP_TOKEN` equal to `API_TOKEN_ADMIN`. Elevation requires all three configured distinct API tokens; an invalid or missing credential fails startup. No request argument can elevate the process role.

Read tools: `list_court_sources`, `get_source_capabilities`, `search_cases`, `search_docket_entries`, `search_filing_text`, `get_case`, `get_case_docket`, `get_filing`, `get_document_text`, `get_job_status`, `get_coverage_report`, `get_refresh_policy`, `get_case_interpretation`, `health`.

Acquire tools: `request_case_acquisition`, `request_bulk_search`, `request_case_refresh`, `set_case_watch` (plus read tools). These are the canonical MCP names; internal CLI/REST operation names are not exposed as duplicate MCP aliases.

Admin tools: `retry_job`, `cancel_job`, `restrict_case`, `control_source`, `plan_discovery`, `schedule_due`, `set_refresh_policy`, `get_retention_policy`, `set_retention_policy`, `request_retention`, `get_retention_request`, `run_retention`, `request_case_interpretation`, `import_legacy`, `verify_storage`, `metrics` (plus lower-role tools).

MCP inputs use the same JSON fields as REST, with path parameters included as `id` or `sourceId` and `idempotencyKey` in the tool arguments rather than an HTTP header. For example: `request_case_acquisition({query:{sourceId:"mn-mcro",searchType:"case",caseNumber:"27-CV-24-1"},idempotencyKey:"request-1"})`. Tool definitions include runtime input schemas and read-only/destructive annotations. Unknown operation fields and out-of-range pagination fail before service calls; bulk query items are validated individually by the service. Tool errors carry `isError: true` and a sanitized JSON error; successful text content contains the service JSON result. Process shutdown closes the transport and application resources.

## Source administration and interpretation

`courtctl source enable|disable|pause|resume --source SOURCE --reason TEXT [--minutes N]` changes persisted administrative state. Pause duration defaults to 60 minutes, bounded 1–10080; duration on other actions is rejected. REST: admin-only `POST /api/v1/sources/:sourceId/control` with `{action,reason,minutes?}`. MCP: `control_source`. Bootstrap never overwrites enabled state. Resume clears the shared pause but does not reset job retry deadlines or enable a disabled source. These controls are **not access authorization**. Production Minnesota workers additionally require reviewed permission and their own `COURT_ALLOW_LIVE_MN=true`; read-only processes cannot claim live work.

`courtctl case interpretation UUID` reads the latest still-current evidence-grounded optional run. `case interpret UUID --idempotency-key KEY` queues administrator-requested inference only when both model and case-level opt-ins are enabled. REST GET/POST `/api/v1/cases/:id/interpretation`; POST uses Idempotency-Key. No paid inference is necessary for search, extraction, OCR or local acceptance. See [processing](PROCESSING.md) and [retention](RETENTION.md).

Source `citationNumber` selects the portal's citation-number search, not legal authority. Database `citation` matches extracted `case_number`, `reporter_citation`, `statute` and `rule` mentions. Filing text's citation/type predicates correlate to the returned document and its latest valid current-version extraction. Labels or hierarchical classification families may match `documentType`; older classifications cannot satisfy a current filter.
